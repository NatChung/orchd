# Channel setup on a new machine

1. Follow the README installation section and run `orchd install`. For Slack, install the optional dependency in the same environment as orchd: for a checkout, `uv sync --extra channels-slack`; for the README uv tool install, reinstall with `uv tool install --force --with slack-sdk git+https://github.com/NatChung/orchd.git` and rerun `orchd install`. State: the channel layout exists but sources remain disabled.
2. Run `orchd channels setup --dry-run` to preview choices without storing tokens or changing channel data. State: nothing is provisioned. Run `orchd channels setup` to configure a source. Choose Slack or LINE and follow its printed platform steps. For Slack, create an app using the printed manifest, enable Socket Mode, create an app-level token with `connections:write`, install the app and invite its bot to the target conversation. Collect the workspace ID, conversation ID, app token and bot token. For LINE, create a Messaging API channel, collect its channel secret and conversation ID, and arrange a public HTTPS endpoint yourself. Set the webhook to `https://YOUR-ENDPOINT/webhook` (or `/webhook/SOURCE` for multiple LINE sources). State: the external account is ready; LINE's endpoint is still your responsibility.
3. Enter a unique source ID, workspace or channel ID, conversation ID and owner Orch ID. Enter tokens only at the hidden prompts. The wizard stores them in Windows Credential Manager or macOS Keychain, creates the source and route, enables the source, and prints doctor output. State: the source and route exist and are enabled; inspect `orchd channels doctor` for health. If setup fails partway, inspect `orchd channels source list`, `route list`, and `secret list --adapter ADAPTER --source SOURCE` before retrying.
4. Choose whether to install the per-user service. You can also run `orchd channels service install` later. Windows registers a logon task and starts it; macOS registers a LaunchAgent and starts it. State: use `orchd channels service status` to see registration, whether a receiver holds the lock, last received timestamp if available, and log path. The log and `serve.lock` live in the channel home. `orchd channels service stop` stops it; `orchd channels service uninstall` unregisters it. On Windows, stop before uninstalling if it is running. A stopped service starts at the next login unless uninstalled.
5. Send a test message to the configured conversation. Check service status and `orchd channels messages --source SOURCE`. State: a received message appears locally; absence of a recent message alone does not prove the service is offline. Check the log and doctor if it does not arrive.

The service runs under the signed-in user and needs access to the installed executable, channel home, state database, and unlocked OS secret store. It receives only while the machine and service are running; LINE needs the separately managed HTTPS endpoint and cannot recover events never accepted. This setup does not create a LINE tunnel or enable outbound sending. For an existing legacy receiver, stop and fence it first; follow [the rollout procedure](channels-rollout.md) rather than run two receivers.
